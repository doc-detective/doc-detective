[`github-action`](https://github.com/doc-detective/github-action) is a TypeScript-based GitHub Action that runs Doc Detective in GitHub workflows. Doc Detective can run in any CI/CD environment, but this GitHub Action simplifies running it in GitHub workflows. It also provides a `results` output, a JSON string you pass through `fromJSON()` to read in later steps. It offers handy features too, like creating GitHub issues for failed tests.

This repo depends on [`doc-detective`](doc-detective) for performing the tests.

## Issue notifications

The GitHub Action can automatically create GitHub issues when tests fail. Set `create_issue_on_fail` to `true` to enable this.

### Basic issue configuration

- `create_issue_on_fail`: Creates a GitHub issue when any test fails. If an open issue has the same `issue_title` and the first label in `issue_labels`, the action updates that issue instead.
- `issue_title`: Title of the created issue. Default: `"Doc Detective Failure"`.
- `issue_body`: Body of the issue. Default: `A Doc Detective run ($RUN_URL) failed:`, a blank line, then `$SUMMARY`. Supports these variables:
  - `$SUMMARY`: Markdown summary of the run, from the run folder's `testResults.md`. See [Find reports and the run folder](/docs/ci/github-action#find-reports-and-the-run-folder).
  - `$RUN_URL`: URL of the workflow run that created the issue.
  - `$RESULTS`: Test results as a JSON code block.
  - `$PROMPT`: The prompt text (see below).
- `issue_labels`: Comma-separated list of labels to apply.
- `issue_assignees`: Comma-separated list of GitHub usernames to assign.

### AI issue mentions

Mention AI assistants in created issues to help investigate and fix failures faster. Use `issue_mentions` to specify which assistants to mention.

- `issue_mentions`: Comma-separated list of assistants to mention. Supported values:
  - `doc-sentinel`: Adds the line `/cc @reem-sab`, without the prompt
  - `promptless`: Mentions `@promptless` with the prompt
  - `dosu`: Mentions `@dosu` with the prompt
  - `claude`: Mentions `@claude` with the prompt
  - `cursor`: Mentions `@cursor` with the prompt
  - `opencode`: Uses the `/opencode` command with the prompt
  - `copilot`: Auto-assigns the issue to Copilot (instead of adding to the accordion)
  
  Mentions (except `copilot`) appear in a collapsible section in the issue body. The action ignores unsupported values and logs a warning.

- `issue_prompt`: Text that follows each mention. You can also use `$PROMPT` in your custom `issue_body` template. Default: `"Investigate potential causes of the failures reported in this Doc Detective test output and suggest fixes."`.

### Example

```yaml
- uses: doc-detective/github-action@v2
  with:
    input: ./docs
    create_issue_on_fail: true
    token: ${{ secrets.DOC_DETECTIVE_ISSUE_TOKEN }}
    issue_mentions: claude,copilot
    issue_prompt: "Analyze these test failures and suggest documentation fixes"
```

Action `@v2` renamed `integrations` to `issue_mentions` and `prompt` to `issue_prompt`. The old names still work as deprecated aliases that log a warning, and setting both an old and a new name fails the job. For the user-facing guide, see [AI issue mentions](/docs/ci/issue-mentions).

`claude` needs `token`, because GitHub doesn't start Claude Code's workflow for an issue that the default `GITHUB_TOKEN` opens. See [Hand off test failures to an AI agent](/ai/ai-agents/hand-off-failures).

## Commits and releases

Merging a pull request to `main` can release a new version of the action, and the commit types decide whether it does. Write every commit in the [Conventional Commits](https://www.conventionalcommits.org/) format. Pull requests merge with merge commits, so every commit in a pull request reaches `main` and counts toward the release.

A `commitlint` check runs on each pull request and checks its commits. It skips merge commits and the commits `git revert` writes, but no author is exempt, including Dependabot. For a revert commit, that skip covers only the format check. The release workflow still counts the commit, so merging it cuts a patch release. If the check fails, reword the commit with `git rebase -i` and force-push your branch.

Each commit type maps to a version bump. When a merge brings in several types, the largest bump wins:

| Commit type | Version bump |
|---|---|
| `fix:`, or a commit that `git revert` writes | patch (X.Y.**Z+1**) |
| `feat:` | minor (X.**Y+1**.0) |
| Any type with `!` after it, such as `feat!:` or `docs!:`, or with a `BREAKING CHANGE:` footer | major (**X+1**.0.0), only when a maintainer approves it |
| Any other type, such as `docs:`, `ci:`, `chore:`, `test:`, `refactor:`, and `perf:` | no release |

When a revert and the commit it reverts land in the same release, neither one counts toward the version bump.

A maintainer must approve each major release. Unless the `ALLOW_MAJOR_RELEASE` repository variable is `true`, the release workflow fails before it tags anything. Every later merge to `main` fails the same way, and no fix or feature gets released, until a maintainer takes one of these steps:

- To release the major, set `ALLOW_MAJOR_RELEASE` to `true` under **Settings** > **Secrets and variables** > **Actions** > **Variables**, re-run the failed workflow, then delete the variable.
- To cancel the major, revert the commit that has the `!` or the `BREAKING CHANGE:` footer. The next release then follows the other commits.

When a merge cuts a release, the release workflow tags `vX.Y.Z` and publishes a GitHub release with generated notes. It then moves the major tag, such as `v2`, to the newest stable release in that major, and moves `latest` to the newest stable release overall. Workflows that use `doc-detective/github-action@v2` get the new release on their next run.
