Add new content, examples, and improvements to the documentation. You can work in your browser or set up a local development environment.

## What counts as a standard contribution

- Adding missing steps to tutorials
- Providing code examples
- Adding troubleshooting tips
- Adding "See also" links
- Expanding brief explanations
- Adding diagrams or screenshots

## Two ways to work

### Option 1: Browser-based (easier)

Use GitHub's web editor for smaller additions:

1. Use the **Edit this page** button on any doc page
2. Make your changes using the web editor
3. Commit and create a pull request

👉 See [Quick changes](quick-start) for detailed instructions.

Good for adding a few paragraphs, code examples, or list items.

### Option 2: Local development (more powerful)

Set up a local environment to preview changes as you write:

👉 See [Local Development Setup](local-development) for detailed instructions.

Good for adding multiple sections, working across multiple files, or seeing live previews.

## Using content templates

Templates help you structure your contribution and ensure you include all the important information.

Choose the template that matches what you're creating:

| Template | Purpose |
| --- | --- |
| [How-to guide](./content-templates/how-to) | Task-focused step-by-step instructions |
| [Tutorial](./content-templates/tutorial) | Learning-oriented guide through a complete workflow |
| [Troubleshooting entry](./content-templates/troubleshooting) | Problem-solution format |
| [Reference](./content-templates/reference) | Technical specifications or API documentation |
| [Feature documentation](./content-templates/feature) | Document a new or changed feature |

## Content guidelines

### Structure your content

Use clear headings to organize information:

```markdown
## Before you begin

Prerequisites and setup information

## Step 1: First major action

Detailed instructions

## Step 2: Next major action

More instructions

## What's next

Related topics and next steps
```

### Write clear instructions

✅ **Do**

- Use second person ("you") and active voice
- Start steps with action verbs: "Click", "Type", "Navigate"
- Put conditions before instructions: "If you want to save, click **Save**"
- Use numbered lists for sequential steps
- Use bulleted lists for non-sequential items

⛔ **Don't**

- Use first person ("we") or passive voice
- Start steps with "Now" or "Then"
- Bury conditions in the middle of instructions
- Mix ordered and unordered lists

### Code examples

Always test code examples before submitting:

````markdown
```json title="example-test.spec.json"
{
  "tests": [
    {
      "steps": [
        {
          "goTo": "https://doc-detective.com"
        }
      ]
    }
  ]
}
```
````

Include

- **Language identifier**: json, bash, typescript, etc.
- **File name** (optional): Use `title="filename.ext"`
- **Context**: Explain what the code does before showing it

The repository's tests check `json` and `yaml` examples that look like a Doc Detective spec, test, step, or config against the Doc Detective schemas. See [Example validation](#example-validation).

To show a deliberately incomplete or wrong example in a `json` or `yaml` block, add `invalid` to the fence's info string and pair it with a `title`. The check skips that block, and the title hides the marker on the rendered page:

````markdown
```json title="broken-step.json" invalid
{
  "goTo": 42
}
```
````

Without a `title`, the page shows "invalid" as the block's title.

### Links and references

Link to related documentation:

```markdown
See [Actions](/docs/actions) for available test actions.
```

Use

- **Absolute paths** for internal links: `/docs/path/to/page`
- **HTTPS** for external links: `https://example.com`
- **Descriptive link text**: Not "click here" or "this link"

## Before submitting

### Run automated checks locally (optional)

If you're working locally, run these commands from the repository root before submitting. Each command runs in `docs/` through a subshell, so your shell stays in the root.

Set up what each command needs first:

- `fern check` needs the docs dependencies from [Install dependencies](/contribute/contribute/local-development#install-dependencies).
- `vale` needs Vale from [System requirements](/contribute/contribute/local-development#system-requirements) and the `mdx2vast` parser, a global npm package that reads `.mdx` files, from [Style checking with Vale](/contribute/contribute/local-development#style-checking-with-vale).

```bash
# Validate the Fern configuration and pages
(cd docs && npx fern check)

# Run style checks from the docs/ directory
# The glob skips the generated schema reference pages, as CI does
(cd docs && vale '--glob=!fern/pages/reference/schemas/**' fern/pages/)
```

Don't worry if you skip these. The CI/CD pipeline runs them automatically.

### Review your changes

Before creating a pull request:

1. Read your changes out loud. Does it make sense?
2. Test any code examples or commands.
3. Check that links work.
4. Verify screenshots are clear and relevant.
5. Make sure formatting looks correct.

### Create a pull request

1. **Title**: Briefly describe what you added. Examples:

   - ✅ `Add troubleshooting guide for browser detection`
   - ✅ `Document file upload action with examples`

2. **Description**: Use the PR template to provide context:

   - What did you add or change?
   - Why is this helpful?
   - Related issue number (if applicable)

3. **Submit**: Create your pull request.

## What happens during review

1. **Automated checks** run (typically 2-5 minutes)
2. **Maintainer reviews** your contribution (within 5 business days)
3. **Feedback or approval**:
   - If changes are needed, update your pull request.
   - If approved, your contribution is merged.

### Understanding automated checks

#### Vale (style checking)

Vale enforces the documentation style guide. The check fails on any error-level alert, so fix every error Vale reports. The most common errors are em dashes and sentences longer than 25 words.

Vale also reports warnings and suggestions when you run it locally. Common ones include:

- Use "you" instead of "the user"
- Avoid "please" in instructions
- Use active voice instead of passive
- Avoid gendered pronouns (use "they")

Warnings and suggestions don't fail the check. Reviewers use judgment on them.

#### Link validation

Checks that all links work. If the check fails:

- Verify external URLs are correct
- Check internal link paths (case-sensitive)
- Make sure linked pages exist

#### Build check

Checks that the documentation site builds. Failures usually indicate one of these problems:

- Markdown syntax errors
- Missing closing tags
- Invalid front matter

#### Example validation

The test suite validates `json` and `yaml` code examples in `docs/fern/pages/`, the root `README.md`, and `src/common/README.md`. It recognizes a block by its top-level keys:

- A `tests` key makes it a spec.
- A `steps` array that contains an action makes it a test.
- Only step fields, at least one of them an action such as `goTo` or `httpRequest`, make it a step.
- Only configuration keys make it a config.

Each recognized block must pass the Doc Detective schema for its type. The check skips blocks marked `invalid` and any JSON or YAML it doesn't recognize, such as workflow files, API responses, and output samples.

The check runs with the code tests, which a pull request that only changes `docs/` doesn't trigger. A broken example in that pull request then fails the next pull request that changes code. To catch problems before you submit, run the check in a local clone of the `doc-detective/doc-detective` repository. It needs Node.js 24.15 or later but not a browser. From the repository root, install dependencies, compile the schemas the check reads, and run it:

```bash
npm ci
npm run build
npx mocha test/doc-examples.test.js
```

A passing run reports how many blocks it checked and skipped, with `0 invalid`. A failure names the file, the line, and the schema error. Fix the example so it matches the schema. Don't mark it `invalid` to silence the failure: reserve `invalid` for examples that show wrong input on purpose.

## Need help?

### During writing

- **Not sure about structure?** Check similar pages in the docs.
- **Questions about content or technical details?** Ask in [Discord](https://discord.gg/2M7wXEThfF).

### After submitting

- **Automated checks failed?** Check the details in the PR. Reviewers can help.
- **No response yet?** Wait 5 business days, then ping in the PR.
- **Need to make changes?** Commit to the same branch. The PR updates automatically.
