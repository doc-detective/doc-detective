---
title: Visual matching
description: Locate elements by template image when text and selectors can't reach them.
---

Sometimes an element has no reliable text, ID, or selector to match on: a canvas-rendered control, a custom-drawn icon, a native app widget without automation metadata, or a case where all you have is a cropped screenshot. The `image` finding criterion locates elements **visually**: you provide a template image (an icon file or a cropped screenshot), and Doc Detective finds the region of the screen that matches it.

The `image` criterion works in every element-finding action and sub-action—[`find`](/docs/actions/find), [`click`](/docs/actions/click), [`dragAndDrop`](/docs/actions/draganddrop) sources and targets, [`type`](/docs/actions/type) element targeting, `waitUntil.find` conditions, [`screenshot`](/docs/actions/screenshot) crops, and [`annotate`](/docs/actions/annotate) targets—on every surface: desktop browsers, mobile web, and Windows, macOS, Android, and iOS native apps. The one exception is `screenshot` crops, which work on browser surfaces only. On a native app capture, a crop fails the step rather than silently skipping.

## Provide a template

The `image` value accepts:

- **A path**, resolved relative to your spec like other paths: `"image": "images/gear-icon.png"`
- **An inline data URI**: `"image": "data:image/png;base64,iVBORw0K…"`
- **An object** with options:

```json
{
  "find": {
    "image": {
      "path": "images/gear-icon.png",
      "matchThreshold": 0.9,
      "region": { "elementAria": "Toolbar" }
    }
  }
}
```

The most reliable template is a **crop from a screenshot Doc Detective itself took**, because it's guaranteed to match the screen's scale and rendering. On a browser surface, seed it in the same test with a [`screenshot`](/docs/actions/screenshot) crop, then reference it by the same relative path—or save the screenshot output path into a variable. Screenshot crops are browser-only, so on a native app surface, seed a full-window screenshot instead.

```json
{
  "tests": [
    {
      "steps": [
        { "goTo": "https://example.com/app" },
        {
          "screenshot": {
            "path": "gear-button.png",
            "directory": "images",
            "overwrite": "true",
            "crop": "#gear-button"
          },
          "variables": { "GEAR": "$$screenshotPath" }
        },
        { "click": { "image": "$GEAR" } }
      ]
    }
  ]
}
```

## How matching works

Doc Detective screenshots the surface and runs OpenCV template matching against it, and polls until the element appears or the step times out.

- **Scaling is automatic.** Displays differ (Retina, Windows 125–200% scaling), and a template taken at one scale fails completely against a screen at another. Doc Detective derives the scale of the screenshot it takes and tries the template at a ladder of candidate scales—including the common display ratios—so a template taken on a differently scaled machine still matches. The step reports the matched scale in `outputs.imageMatch.scaleUsed`.
- **The match becomes a real element wherever possible.** On browser surfaces, Doc Detective resolves the element under the matched region's center with `document.elementFromPoint`, so every interaction (`click` with buttons and durations, `moveTo`, `type`) and all `outputs.element` details work exactly as with any other criterion. On native app surfaces, Doc Detective recovers the element from the app's accessibility tree. When that isn't possible, the find still succeeds with the matched region's geometry in `outputs.imageMatch`, and a left click falls back to tapping the region's center.
- **Combining criteria narrows geometrically.** When you combine `image` with other criteria (`elementText`, `selector`, and so on), the matched element must satisfy them all: its bounds must contain a visual match's center *and* it must match the other criteria. This is how you tell apart two identical icons with different labels.
- **Ambiguity fails loudly.** If two or more regions match the template and no other criterion distinguishes them, the step fails and names the count, scores, and locations—Doc Detective never silently clicks the first lookalike. Add another criterion or a `region` to narrow the search.

## Tune the match threshold

`matchThreshold` (0–1) is the minimum normalized match score to accept. The default is `0.8`—strict enough to reject lookalikes while tolerating minor rendering variation. Set it per step in the `image` object, or change the default for a whole project with the `imageMatching` config option:

```json
{
  "imageMatching": { "matchThreshold": 0.9 }
}
```

Higher values are stricter (`1` demands a near pixel-perfect match). Lower values tolerate more variation but risk matching the wrong region.

## Narrow the search with a region

`region` restricts where Doc Detective looks—useful to disambiguate identical-looking targets or to speed up matching:

- **A rect** in logical units: `"region": { "x": 400, "y": 0, "width": 400, "height": 300 }`
- **Element criteria** whose matched element's bounds become the search area: `"region": { "selector": "#sidebar" }`

## Diagnose a miss

When a visual find times out, the failure reports how close the highest-scoring candidate came (for example, `Best visual candidate scored 0.71 against threshold 0.8`) and writes an annotated screenshot with the highest-scoring region boxed into the run's artifact folder. The outputs also carry `outputs.imageMiss` with the top score and rect. Common causes:

- **The template is stale**—the UI changed. Take a fresh template screenshot.
- **The element is below the fold**—browser matching covers only the current viewport, and visual finds don't auto-scroll. Scroll first, or use a DOM criterion (which does scroll) alongside the image.
- **The threshold is too strict** for the rendering variation between the template's source and the current surface.

## Limitations

- Matching costs a screenshot plus an OpenCV pass per poll (roughly 0.1–1.5 s each, plus a one-time engine load), so image finds poll less often within a timeout than DOM finds. Give visual steps generous timeouts.
- Browser matching is viewport-bound: content below the fold never matches.
- On an image-only browser find, `outputs.element` describes the **topmost** node at the match center—which can be a child of the logical control, exactly as a real user's click would land.
- Visual matching requires the optional `@appium/opencv` dependency. It installs automatically with `doc-detective install`, with no native build on any supported platform.
