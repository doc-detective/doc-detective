title: Docker and headless
description: Run Doc Detective in the official container and in headless environments, and capture video where no display exists.

Continuous integration runners are usually headless and often containerized. This guide covers running Doc Detective with the official Docker image, what changes when no display is available, and how to record video headlessly.

## Before you begin

- Install Docker if you plan to use the container image.
- Have a spec or input directory you can run.

## Step 1: Run the official container

The official image is `docdetective/docdetective:linux` on Docker Hub. Its entrypoint is the Doc Detective CLI, so anything you pass after the image name goes straight to `doc-detective`. Mount your project so the container can read your tests and write results back out:

```bash
docker run -v .:/app docdetective/docdetective:linux --input /app/api.spec.json
```

The `-v .:/app` flag mounts your current directory to `/app` inside the container. Because the working directory is `/app`, point `--input` and `--output` at paths under `/app` so results and artifacts land back in your project.

<Note>
Inside the official image, unsafe steps run automatically without `--allow-unsafe`. Those include `runCode` snippets detected from Markdown code fences. The image identifies itself as a container, and Doc Detective allows unsafe steps in that environment by default. To opt out, set `allowUnsafeSteps` to `false` in your config.
</Note>

## Step 2: Understand headless behavior

A headless environment has no display, which affects browser-driven tests:

- **Browser tests** run headless automatically when no display is available. On Ubuntu CI runners, Chrome and Firefox contexts fall back to headless mode.
- **Video recording** is the main thing that needs a display. The default browser recording engine captures the Chrome viewport and works headless; the `ffmpeg` engine captures the screen and needs a real or virtual display.

Some tests record video with the `ffmpeg` engine on a headless runner. Run those on a macOS or Windows runner instead, where a display is available. For engine details, see [Record video](/docs/test-docs/record-video).

## Step 3: Warm runtime assets

Doc Detective installs heavy assets on first use, including browsers, drivers, and npm packages. In CI, install them ahead of time and cache them so each run starts fast.

Point the cache at a workspace path with `DOC_DETECTIVE_CACHE_DIR`, then pre-install everything with `doc-detective install all`:

```bash
export DOC_DETECTIVE_CACHE_DIR="$PWD/.doc-detective-cache"
doc-detective install all --yes
```

On a fresh `npm install`, Doc Detective also pre-warms these assets automatically. To skip that step, set `DOC_DETECTIVE_AUTOINSTALL=0`. That's useful when you want to control exactly when assets download in CI. The official container ships with assets already warmed, so you don't need this step inside it.

Each run front-loads whatever the cache is missing. Before executing tests, Doc Detective plans the installs, device boots, and downloads its tests need, then runs them concurrently as a warm phase. With a persisted cache the phase completes in milliseconds. On a cold cache it overlaps the downloads instead of paying them one test at a time. The per-task timings land in the JSON results. See [Read the warm-phase timings](/docs/ci/reporters-and-artifacts#read-the-warm-phase-timings).

<Note>
`docdetective/docdetective:linux` is a multi-arch image covering `linux/amd64` and `linux/arm64`. Chrome and ChromeDriver have no native `linux/arm64` build upstream, because Google's Chrome for Testing only publishes x64 binaries. On the `linux/arm64` variant, Chrome and ChromeDriver pre-warming is skipped rather than failing the image. To run Chrome-driven tests on arm64 hosts, run the `linux/amd64` variant under emulation, or use Firefox instead. Firefox and GeckoDriver both ship in the image for arm64 and run natively, so a Firefox context needs no extra setup.
</Note>

For a GitHub Actions caching recipe, see [Runtime caching](/docs/ci/github-action#runtime-caching).

## Step 4: Run headless in CI

Put the pieces together in a generic, platform-agnostic pipeline step. The CLI exits non-zero when a test fails, so a failing spec fails the step:

```bash
docker run -v .:/app \
  -e DOC_DETECTIVE_AUTOINSTALL=0 \
  docdetective/docdetective:linux \
  --input /app/docs --output /app/results.json
```

`docker run` returns the container's exit code, so the step fails whenever any spec's result is `FAIL`, or whenever nothing valid was tested. For the full list of exit codes and other ways to gate the build, see [Reporters and artifacts](/docs/ci/reporters-and-artifacts#step-6-fail-ci-when-tests-fail).

## Provide credentials from files

Containers and CI systems often mount secrets as files. Doc Detective can read credentials from a file, so they stay out of your config file and the environment:

| Setting | Holds |
|---|---|
| `DOC_DETECTIVE_API_FILE` environment variable | Path to a JSON file with the same contents as `DOC_DETECTIVE_API`. When both are set, the file wins. |
| `integrations.docDetectiveApi.apiKeyFile` config key | Path to a file holding the Orchestration API key. Use it in place of `apiKey`. |
| `integrations.heretto[].apiTokenFile` config key | Path to a file holding a Heretto API token. Use it in place of `apiToken`. See [Heretto](/docs/test-docs/heretto). |

Relative paths resolve from the current directory, and Doc Detective trims whitespace around a key or token. If it can't read a file, the run exits `2` and names the file.

```bash
docker run -v .:/app \
  -v /run/secrets/doc-detective-api.json:/secrets/api.json:ro \
  -e DOC_DETECTIVE_API_FILE=/secrets/api.json \
  docdetective/docdetective:linux
```

## Verify it works

- The container run prints a terminal summary and writes results to the path you passed to `--output`.
- Browser tests complete without a display error.
- If you pre-warmed assets, the run starts without downloading browsers or drivers.

## Troubleshooting

### A recording step is skipped or fails on a headless runner

**Cause:** The `ffmpeg` recording engine needs a display, which a headless Linux runner doesn't have.

**Solution:** Use the browser recording engine for headless captures, or move recording tests to a macOS or Windows runner. See [Record video](/docs/test-docs/record-video).

### Runs are slow because assets download every time

**Cause:** The runtime cache isn't persisted between runs.

**Solution:** Set `DOC_DETECTIVE_CACHE_DIR` to a path your CI caches, and pre-install with `doc-detective install all --yes`. See [Runtime caching](/docs/ci/github-action#runtime-caching).
