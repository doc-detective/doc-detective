The [Doc Detective GitHub Action](https://github.com/doc-detective/github-action) runs your tests inside a GitHub Actions workflow. It's the recommended way to run Doc Detective in CI. It installs Doc Detective for you and fails the job when tests fail. It can also open a pull request or file an issue when a run finds a problem. This guide covers adding the action to a workflow, failing the build on test failures, and wiring up the pull request and issue features.

For the full list of inputs and outputs, see the [action's README](https://github.com/doc-detective/github-action).

## Before you begin

- A GitHub repository with documentation tests. That's either a spec you can run, or docs with inline or detected tests.
- Permission to add a workflow file under `.github/workflows/` in that repository.

## Step 1: Add the action to a workflow

Create a workflow file in `.github/workflows/`. Check out the repository first so the action can read your tests. Set up Node.js, then add the Doc Detective step:

```yaml title=".github/workflows/doc-detective.yml"
name: doc-detective
on: [pull_request]

jobs:
  doc-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - uses: doc-detective/github-action@v2
```

This runs Doc Detective on every pull request. Doc Detective 5 needs Node.js 24.15 or later, and GitHub-hosted runners default to an older version. On older Node.js, the action warns:

```text
Doc Detective 5 needs Node.js 24.15 or later, but this job runs <version>. Add `actions/setup-node` with `node-version: 24`.
```

Pin to the major version (`@v2`) to pick up fixes automatically, or pin to a full version such as `@v2.0.0` for a fixed release. Action `@v2` runs CLI 5, and `@v1` stays on CLI 4. If you're moving from `@v1`, see [Upgrade to Doc Detective 5](/docs/ci/upgrade-to-v5).

## Step 2: Point the action at your tests

By default, the action runs from the repository root and uses the config file Doc Detective discovers there. To override either one, set the corresponding input:

```yaml
- uses: doc-detective/github-action@v2
  with:
    version: 5
    config: .doc-detective.json
    input: ./docs
```

| Input | Default | Description |
|---|---|---|
| `version` | `5` | Doc Detective version to run, as a version number, a range such as `^5`, or an npm tag such as `latest`. Action `@v2` expects version 5 or later. Leave it empty (`""`) to run a locally resolvable build instead of installing from the registry. |
| `working_directory` | `.` | Directory to run in, relative to the repository root. |
| `config` | None | Path to a configuration file, relative to `working_directory`. |
| `input` | None | Path to an input file or directory, relative to `working_directory`. Overrides the `input` field in the config file. |

<Note>
Leave `version` empty to skip the registry install and run whatever `doc-detective` is already resolvable in the working directory. One example is a local build you exposed with `npm link` in an earlier step. This lets a repository test the action against its own build under review rather than the published package. The action expects version 5's exit codes, so the local build must be version 5 or later.
</Note>

## Step 3: Fail the build when tests fail

By default, a failing test fails the job and blocks the pull request. To report failures without failing the job, for example while you triage an existing suite, set `exit_on_fail` to `false`:

```yaml
- uses: doc-detective/github-action@v2
  with:
    exit_on_fail: false
```

The action follows the exit code from the CLI:

| CLI exit code | Result |
|---|---|
| `0` | The job passes. |
| `1` | At least one test failed. The job fails unless `exit_on_fail` is `false`. |
| `2` | Nothing valid was tested, such as a mistyped `input`, an invalid config, or every test skipping. The job always fails. |
| Any other code | The run didn't finish, for example `130` after an interrupt. The job always fails. |

The job also fails when the CLI writes no results file, whatever `exit_on_fail` says. The action treats that as a run that never happened, not as a failing test. For example, a network error while `npx` installs Doc Detective exits `1` with no results.

When the CLI does write results, the action sets the `results` output and runs the issue and pull request steps before it fails the job.

`exit_on_fail` acts only on exit code `1`. If a test fails but the CLI exits `0`, the job passes and the action logs a warning. The CLI exits `0` on a failing test when your config sets `exitOnFail: false`, or when `version` runs a CLI older than 5. To stay on CLI 4, use `doc-detective/github-action@v1`.

See [Reporters and artifacts](/docs/ci/reporters-and-artifacts#step-6-fail-ci-when-tests-fail) for the exit codes in detail.

## Step 4: Open a pull request when files change

Doc Detective sometimes updates files during a run, refreshing screenshots or recording new command output. The action can commit those changes to a branch and open a pull request for review. To enable this, set `create_pr_on_change` to `true` and grant the job permission to write contents and pull requests:

```yaml
name: doc-detective
on:
  schedule:
    - cron: '0 0 * * *'  # Run daily at midnight

jobs:
  doc-tests:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - uses: doc-detective/github-action@v2
        with:
          create_pr_on_change: true
          pr_paths: docs/images
          pr_title: Doc Detective found changes
          pr_labels: doc-detective,for-review
```

The action commits to one branch, `doc-detective-changes` by default, and force-pushes it on each run. If that branch already has an open pull request, the action updates it rather than opening another. The pull request targets `GITHUB_BASE_REF`, the base of the pull request that triggered the run. Otherwise it targets `GITHUB_REF_NAME`, the branch the run is on. Git commands run in `working_directory`.

<Warning>
By default, the action stages every changed file, including screenshots and recordings the run takes. They can show unreleased UI or customer data. Set `pr_paths` to limit what the pull request commits.
</Warning>

<Note>
You must allow GitHub Actions to create pull requests for the repository. Go to **Settings** > **Actions** > **General** and select **Allow GitHub Actions to create and approve pull requests**.
</Note>

| Input | Default | Description |
|---|---|---|
| `create_pr_on_change` | `false` | Open or update a pull request if any files change during the run. |
| `pr_paths` | None | Comma-separated paths to stage, relative to `working_directory`. When unset, the action stages every changed file. |
| `pr_branch` | `doc-detective-changes` | Branch for the pull request. The action force-pushes it on each run. |
| `pr_title` | `Doc Detective Changes` | Pull request title. |
| `pr_body` | See README | Pull request body. `$RUN_URL` inserts the workflow run URL. |
| `pr_labels` | `doc-detective` | Comma-separated labels. |
| `pr_assignees` | None | Comma-separated usernames to assign. |
| `pr_reviewers` | None | Comma-separated usernames to request reviews from. |

A created pull request means files changed, not that tests passed or failed. Review the diff before merging.

## Step 5: File an issue when tests fail

When a run has failing tests, the action can open a GitHub issue to track the failure and mention an AI assistant to investigate it. To enable this, set `create_issue_on_fail` to `true` and grant the job permission to write issues:

```yaml
name: doc-detective
on: [pull_request]

jobs:
  doc-tests:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      issues: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - uses: doc-detective/github-action@v2
        with:
          create_issue_on_fail: true
          issue_title: Doc Detective found documentation issues
          issue_mentions: claude
```

| Input | Default | Description |
|---|---|---|
| `create_issue_on_fail` | `false` | Open or update an issue if one or more tests fail. |
| `issue_title` | `Doc Detective Failure` | Issue title. |
| `issue_body` | `A Doc Detective run ($RUN_URL) failed:`, a blank line, then `$SUMMARY` | Issue body. `$SUMMARY` inserts the run's summary, `$RESULTS` the results object, `$RUN_URL` the workflow run URL, and `$PROMPT` the `issue_prompt` text. |
| `issue_labels` | `doc-detective` | Comma-separated labels. |
| `issue_assignees` | None | Comma-separated usernames to assign. |
| `issue_mentions` | None | Comma-separated AI assistants to mention in the issue. See [AI issue mentions](/docs/ci/issue-mentions). |
| `issue_prompt` | `Investigate potential causes of the failures reported in this Doc Detective test output and suggest fixes.` | Text that follows each mention. |

If an open issue has the same title and the first label in `issue_labels`, the action updates that issue. Otherwise it creates one. A daily schedule then keeps one issue current rather than opening one per run.

`$SUMMARY` is the run folder's `testResults.md`, the run's Markdown summary. When the run wrote no run folder, it reads `Doc Detective wrote no summary for this run. See the workflow run.`

`$SUMMARY` and `$RESULTS` come from masked output, so environment variable values appear as `***NAME***`. GitHub masks secrets in logs but not in issue bodies, so this keeps them out of the issue. See [Keep secrets out of logs, reports, and captures](/docs/ci/secrets).

GitHub limits an issue body to 65,536 characters. When the body would be longer, the action shortens `$SUMMARY` or `$RESULTS` to fit. A shortened `$RESULTS` ends with a link to the workflow run. If `issue_body` and `issue_prompt` leave no room for results, the action logs an error and doesn't create the issue.

The `issue_mentions` input mentions an AI assistant in the issue so it can investigate the failure and suggest a fix. Options include `claude`, `copilot`, `cursor`, and `promptless`. For the full list, see [AI issue mentions](/docs/ci/issue-mentions).

<Note>
GitHub Action `@v2` renames `integrations` to `issue_mentions` and `prompt` to `issue_prompt`. The old names still work, but the action logs a deprecation warning. Setting both an old and a new name fails the job before tests run.
</Note>

## Step 6: Use the results in later steps

The action exposes the run's results so later steps can act on them. Give the step an `id`, then read its outputs:

```yaml
- uses: doc-detective/github-action@v2
  id: doc-detective
- run: echo "Results: ${{ steps.doc-detective.outputs.results }}"
```

| Output | Description |
|---|---|
| `results` | JSON-formatted test results. |
| `pull_request_url` | URL of the pull request, when `create_pr_on_change` opens or updates one. |
| `issue_url` | URL of the issue, when `create_issue_on_fail` opens or updates one. |

## Find reports and the run folder

The action passes Doc Detective a temporary path with `--output`, and reads the results file from there to set the `results` output. Use that output rather than the file.

Everything else lands under your config's `outputDir`, as it does on the command line. That's the run folder, `<outputDir>/.doc-detective/runs/<runId>/`, and files from reporters you turn on with `reporters`, such as `junit.xml`. `outputDir` defaults to the config file's folder, or `working_directory` with no config file. See [Choose your reporters](/docs/ci/reporters-and-artifacts#step-1-choose-your-reporters).

The action adds `.doc-detective/`, `junit.xml`, `doc-detective-summary.md`, and `testResults-*` to `.git/info/exclude`. Git then ignores them, so `create_pr_on_change` doesn't commit the run's own reports. Screenshots and recordings aren't excluded. A `screenshot: true` image lands in `outputDir`, beside the reference image you committed, so each run compares against it. A changed image reaches the pull request. To keep images out of the pull request, set `pr_paths`.

GitHub discards the checkout when the job ends. To keep the reports, upload them in a later step. This example assumes `outputDir` is the repository root. Leave out any path your config doesn't produce:

```yaml
- uses: doc-detective/github-action@v2
- if: always()
  uses: actions/upload-artifact@v4
  with:
    name: doc-detective-run
    path: |
      junit.xml
      .doc-detective/runs/
    include-hidden-files: true
```

`if: always()` uploads the files even when a failing test fails the job. `upload-artifact` treats files in a folder whose name starts with `.` as hidden and skips them by default, so set `include-hidden-files: true` to upload the run folder. Upload the run folder with `junit.xml`, because its [attachments](/docs/ci/reporters-and-artifacts#read-the-junit-report) are relative to that file.

## Browser modes

On Ubuntu runners, the action runs browsers headless. Chrome and Firefox contexts fall back to headless mode automatically.

Some tests need a display, such as recording video with the `ffmpeg` engine. Run those jobs on a macOS or Windows runner instead:

```yaml
jobs:
  doc-tests:
    runs-on: macos-latest  # or windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - uses: doc-detective/github-action@v2
```

See [Docker and headless](/docs/ci/docker-and-headless) for how headless environments affect a run.

## Speed up iOS tests on macOS

Tests against the `ios` platform run on macOS runners, where the first XCUITest session compiles WebDriverAgent with `xcodebuild`. On a cold, ephemeral runner, that compile takes around 10 minutes. To pay that cost once, persist Doc Detective's [cache directory](/reference/reference/cli/install#cache-directory) between runs, then run [`doc-detective install ios --yes`](/reference/reference/cli/install#install-ios) in your setup steps. It compiles WebDriverAgent once into the cache, keyed by your Xcode **and** XCUITest driver versions. Test sessions use the build automatically and read-only, which is safe to share across parallel jobs.

```yaml
jobs:
  doc-tests:
    runs-on: macos-latest
    env:
      DOC_DETECTIVE_CACHE_DIR: ${{ github.workspace }}/.dd-cache
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - uses: actions/cache@v4
        with:
          path: .dd-cache
          key: dd-cache-${{ runner.os }}
      - run: npx doc-detective install ios --yes
      - uses: doc-detective/github-action@v2
```

## Runtime caching

Doc Detective installs heavy runtime assets on first use, including browsers, drivers, and npm packages. To speed up CI, cache them between runs.

### Cache the runtime directory

Point `DOC_DETECTIVE_CACHE_DIR` at a path under the workspace, then use GitHub's cache action to persist it between runs:

```yaml
jobs:
  doc-tests:
    runs-on: ubuntu-latest
    env:
      DOC_DETECTIVE_CACHE_DIR: ${{ github.workspace }}/.doc-detective-cache
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - uses: actions/cache@v4
        with:
          path: .doc-detective-cache
          key: doc-detective-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
          restore-keys: |
            doc-detective-${{ runner.os }}-
      - uses: doc-detective/github-action@v2
```

Because `DOC_DETECTIVE_CACHE_DIR` points to a path under `${{ github.workspace }}`, the cache action can store and restore those assets across runs.

### Pre-install assets

To control exactly when assets download, install them before the action runs:

```yaml
jobs:
  doc-tests:
    runs-on: ubuntu-latest
    env:
      DOC_DETECTIVE_CACHE_DIR: ${{ github.workspace }}/.doc-detective-cache
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - uses: actions/cache@v4
        with:
          path: .doc-detective-cache
          key: doc-detective-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
          restore-keys: |
            doc-detective-${{ runner.os }}-
      - run: npm install -g doc-detective
      - run: doc-detective install all --yes
      - uses: doc-detective/github-action@v2
```

Setting `env` at the job level makes `DOC_DETECTIVE_CACHE_DIR` visible to every step, so the pre-install step and the action share the same cached directory.

## Verify it works

Open a pull request that touches a documented command, screenshot, or API response, then confirm:

- The `doc-detective` job runs and its log shows the terminal summary.
- A failing test fails the job and blocks the pull request, unless you set `exit_on_fail: false`.
- With `create_pr_on_change: true`, a run that changes files opens a pull request, or updates the open one.
- With `create_issue_on_fail: true`, a run with failing tests opens an issue, or updates the open one.

## Troubleshooting

### The job passes even though a test failed

**Cause:** One of these settings keeps the job green:

- The step sets `exit_on_fail: false`.
- The workflow still uses `@v1`, where `exit_on_fail` defaults to `false`.
- Your config sets `exitOnFail: false`, or `version` runs a CLI older than 5. The CLI then exits `0` when a test fails, and the job log shows a warning.

**Solution:** Use `@v2`, remove `exit_on_fail: false` from the step and `exitOnFail: false` from your config, and remove any `version` value below 5. See [Step 3](#step-3-fail-the-build-when-tests-fail).

### Reports or the run folder aren't where you expect

**Cause:** They land under your config's `outputDir`, which resolves against the config file's folder. The action writes only the results file to a temporary path.

**Solution:** Check `outputDir` in your config, or read the `results` output. See [Find reports and the run folder](#find-reports-and-the-run-folder).

### The pull request commits screenshots

**Cause:** `create_pr_on_change` stages every changed file by default, including screenshots and recordings the run takes.

**Solution:** Set `pr_paths` to the paths the pull request should commit. See [Step 4](#step-4-open-a-pull-request-when-files-change).

### The job warns about the Node.js version

**Cause:** Doc Detective 5 needs Node.js 24.15 or later, and the job runs an older version.

**Solution:** Add `actions/setup-node` with `node-version: 24` before the action. See [Step 1](#step-1-add-the-action-to-a-workflow).

### The action can't create a pull request or issue

**Cause:** The job lacks the required permissions, or the repository doesn't allow Actions to create pull requests.

**Solution:** Add `permissions: { contents: write, pull-requests: write }` for pull requests or `permissions: { issues: write }` for issues. For pull requests, also enable **Allow GitHub Actions to create and approve pull requests** under **Settings** > **Actions** > **General**.

### Runs are slow because assets download every time

**Cause:** The runtime cache isn't persisted between runs.

**Solution:** Set `DOC_DETECTIVE_CACHE_DIR` to a cached workspace path and pre-install assets. See [Runtime caching](#runtime-caching).
