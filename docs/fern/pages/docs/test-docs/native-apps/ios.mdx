Doc Detective can open and drive iOS apps on a managed simulator as part of a test. This experimental workflow launches an app with [`startSurface`](/docs/actions/startsurface), acts on it with the same `find`, `click`, and `type` steps you already use in the browser, and closes it with [`closeSurface`](/docs/actions/closesurface).

<Info>

**Experimental**: Native and mobile app testing is experimental and subject to change.

</Info>

## Before you begin

iOS app tests run only on a **macOS host**. On any other platform, Doc Detective skips the test with a reason rather than failing it, so a mixed-platform spec stays green. The host needs three more things:

- The Xcode command-line tools configured (`xcode-select -p`).
- The simulator control tool available (`xcrun simctl`).
- At least one installed iOS runtime to boot a simulator against.

Prepare the host ahead of time:

```bash
doc-detective install ios --yes
```

This installs the automation driver and prebuilds WebDriverAgent, the agent that drives the simulator. It's macOS-only and isn't part of `install all`. If you skip it, the first iOS test installs the driver on its own. With Doc Detective 5.6.0 or later, it also builds WebDriverAgent. Earlier versions leave that build to Appium during the session. See [WebDriverAgent builds on first use](#webdriveragent-builds-on-first-use) and [`install ios`](/reference/reference/cli/install#install-ios).

## Run your first iOS test

This test targets the `ios` platform and launches the Settings app by its bundle ID on the context's default simulator. It opens a settings screen, takes a screenshot of the window, and closes the app. Settings ships with iOS, so the test needs nothing else installed.

{/* test {"testId":"ios-app-settings","detectSteps":false,"runOn":[{"platforms":["ios"]}]} */}

```json
{
  "tests": [
    {
      "runOn": [
        {
          "platforms": ["ios"]
        }
      ],
      "steps": [
        {
          "description": "Launch the app and wait until it's ready.",
          "startSurface": {
            "app": "com.apple.Preferences",
            "timeout": 180000,
            "waitUntil": {
              "find": { "elementText": "Settings" }
            }
          }
        },
        {
          "description": "Open a settings screen.",
          "click": {
            "elementText": "General"
          }
        },
        {
          "description": "Take a screenshot of the window.",
          "screenshot": {
            "path": "ios-settings.png"
          }
        },
        {
          "description": "Close the app.",
          "closeSurface": { "app": "Preferences" }
        }
      ]
    }
  ]
}
```

{/* step {"stepId":"ios-settings-start","description":"Launch the Settings app and wait until it's ready","startSurface":{"app":"com.apple.Preferences","timeout":180000,"waitUntil":{"find":{"elementText":"Settings"}}}} */}
{/* step {"stepId":"ios-settings-click","description":"Open a settings screen","click":{"elementText":"General"}} */}
{/* step {"stepId":"ios-settings-screenshot","description":"Take a screenshot of the window","screenshot":{"path":"ios-settings.png"}} */}
{/* step {"stepId":"ios-settings-close","description":"Close the app","closeSurface":{"app":"Preferences"}} */}
{/* test end */}

To run this test, save it to a spec file and pass it to Doc Detective:

```bash
doc-detective --input ios-app.spec.json
```

A few things to notice:

- The generous `timeout` (180,000 ms) leaves room for a cold simulator boot. A [first-use WebDriverAgent build](#webdriveragent-builds-on-first-use) runs when no cached build matches your Xcode version and driver. It can take about 10 minutes. With Doc Detective 5.6.0 or later, it runs before the steps and doesn't count toward `timeout`. Run `doc-detective install ios --yes` beforehand to keep that build out of the test run.
- `waitUntil.find` gates readiness. The step holds until an element with the text `Settings` exists. The next step then never runs against a screen that hasn't drawn its controls.
- The app that `startSurface` opens becomes the active surface, so the later steps act on it with no `surface` field. Pass an explicit `surface` on a step, such as `{ "app": "Preferences" }`, to switch to a different surface. That switch sticks for the surface-less steps that follow. `closeSurface` still names the surface to close (`{ "app": "Preferences" }`) because it's a lifecycle step, not an interaction on the active surface. Doc Detective derives the default name `Preferences` from the final dot-segment of the bundle ID. Pass a `name` on `startSurface` to choose your own. See [Target an app surface](/docs/actions/startsurface#target-an-app-surface).
- The [`screenshot`](/docs/actions/screenshot) step takes a fresh screenshot of the app every run, so the picture never drifts out of sync with the current build.

To test an app that isn't already on the simulator, point `install` at an `.app` or `.ipa` bundle. See the [app descriptor](/reference/schemas/app-descriptor) reference for the `install` field.

## Choose the simulator

Without a `device`, an iOS app runs on the context's default simulator, which Doc Detective boots or creates on first use. Set `device` on the context or the `startSurface` step to name a simulator or refine it by `deviceType` (phone or tablet) and `osVersion`. See [Choose the simulator](/docs/actions/startsurface#choose-the-simulator) and the [device descriptor](/reference/schemas/device-descriptor) reference for the full list of fields.

## Target only iOS

Because an app targets one platform, gate the test with a [context](/docs/test-docs/platforms-and-browsers) so it runs only where it can:

```json
{
  "runOn": [
    {
      "platforms": ["ios"]
    }
  ]
}
```

On a host that isn't macOS, the test skips with a reason rather than failing. See [Test across platforms and browsers](/docs/test-docs/platforms-and-browsers) for the full context grammar.

## WebDriverAgent builds on first use

Doc Detective keeps WebDriverAgent builds in its [cache directory](/reference/reference/cli/install#cache-directory), one for each Xcode version and driver. In Doc Detective 5.6.0 and later, an iOS test that finds no build for the current pair builds one before it starts. The build can take about 10 minutes, so don't cancel it. Doc Detective warns in the terminal and the report, and exit codes don't change:

```text
No WebDriverAgent build is cached for this Xcode version, so Doc Detective is building one. The first build takes about 10 minutes. Run `doc-detective install ios --yes` ahead of time to skip the wait.
```

The warning's estimate covers slower machines. On GitHub-hosted `macos-latest` runners, the build takes about 2 to 3 minutes.

To find the matching build, Doc Detective first checks the Xcode version. On a cold Mac, such as a fresh CI runner, that check can take up to 2 minutes during a run's first iOS test. The wait adds to any build time, and it ends before the test's steps run, so don't cancel the run.

Later runs reuse the build until Xcode or the driver changes. To build it ahead of time, for example when you prepare a CI image, run `doc-detective install ios --yes`.

If the build fails, the test still runs, and Appium builds WebDriverAgent during the session instead. Doc Detective warns and names the cause in the last sentence. For example, a build that runs too long warns:

```text
Couldn't build WebDriverAgent before the test, so Appium builds it during the session. The build didn't finish within 20 minutes.
```

Other failures end with a different cause, such as an `xcodebuild` error. To find out why a build failed, run with `-d`, or set `DOC_DETECTIVE_DEBUG=true` in CI, and read the build output. Debug output goes to stderr. See [Troubleshooting setup issues](/docs/troubleshooting/setup-issues). If this build fails but another Doc Detective process finishes one, the test uses that build, and the `Couldn't build WebDriverAgent` warning doesn't appear.

Sometimes the build succeeds, but Doc Detective can't list it in the cache's `installed.json` record. The test still uses the new build, later runs still find it, and exit codes don't change. Doc Detective warns and names the cause in the last sentence, so you know why it happened. For example:

```text
Couldn't update the cache record after building WebDriverAgent, so `installed.json` may not list this build. The cache directory isn't writable.
```

The cause can also be `The disk is full.` or `An unexpected error stopped the update.`

To turn off the first-use build, set `DOC_DETECTIVE_NO_IOS_AUTOINSTALL=1`. The test still runs, and Appium builds WebDriverAgent during the session, outside the cache directory. Setting `DOC_DETECTIVE_IOS_WDA_DERIVED_DATA_PATH` to the DerivedData directory of your own WebDriverAgent build also turns it off.

In GitHub Actions, the Doc Detective action v2.2.0 or later (`@v2`) caches the build between runs. Later runs restore it instead of building it. See [Speed up iOS tests on macOS](/docs/ci/github-action#speed-up-ios-tests-on-macos).

## Troubleshooting

**The first app launch is slow**

- **Cause:** No WebDriverAgent build is cached for your Xcode version and driver, so the first iOS test builds one. That can take about 10 minutes. See [WebDriverAgent builds on first use](#webdriveragent-builds-on-first-use).
- **Solution:** Run [`doc-detective install ios --yes`](/reference/reference/cli/install#install-ios) beforehand, so the build happens before the test run. If the build fails and Appium builds WebDriverAgent during the session instead, give the first surface a generous `timeout`.

**Element not found**

- **Cause:** iOS mirrors macOS, mapping element criteria onto accessibility properties. `elementText` matches a control's title, label, or value. `elementId` matches its AXIdentifier. `elementAria` matches its XCUIElementType, and its accessible name when you provide one. `elementText` and `elementAria` collide when a control's accessible name is the same for both, so setting the two fields with different values on one step fails.
- **Solution:** Match against the property that carries the value you want, and specify only one of `elementText` or `elementAria` when they'd target the same accessible name. See [Target an app surface](/docs/actions/startsurface#target-an-app-surface) and the [`find`](/docs/actions/find) reference.

**An element is off-screen**

- **Cause:** The control you want isn't in the visible viewport yet.
- **Solution:** Nothing extra: mobile `find` auto-scrolls toward an off-screen element (up to five steps within the step's timeout) before giving up.

**Pressing a hardware key**

- **Cause:** iOS hardware keys aren't on-screen elements, and not every token works on iOS.
- **Solution:** Send a device-key token with [`type`](/docs/actions/type#device-keys-mobile-app-surfaces): `$HOME$`, `$VOLUME_UP$`, and `$VOLUME_DOWN$` work on iOS. `$BACK$` and `$APP_SWITCH$` fail on iOS; there's no equivalent key.

**A permission dialog blocks the test**

- **Cause:** iOS shows a runtime permission dialog that sits in front of the app.
- **Solution:** Treat the dialog as an element and click it. See [Mobile app surfaces](/docs/actions/click#mobile-app-surfaces).

**Performing a gesture**

- **Cause:** Swipes and scrolls aren't clicks.
- **Solution:** Use the [`swipe`](/docs/actions/swipe) action, which drives iOS gestures.
