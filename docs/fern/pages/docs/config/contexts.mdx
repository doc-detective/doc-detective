title: Contexts
description: Define the contexts (platform and browser combinations) where tests should run.
---

Doc Detective uses contexts to determine *where* tests should run. A context defines a combination of a target platform (operating system) and, optionally, a target browser with specific configurations.

Contexts are sometimes needed but not specified. Doc Detective then runs tests in the first supported browser it finds on the current platform, in this order: Chrome, Firefox, Safari. Browsers run headless unless a context sets `headless: false`. To keep a test on Firefox, name `firefox` in its context.

If no supported browser is available, Doc Detective skips contexts that require browser automation and reports the platform it skipped, for example: ``Skipped: no supported browser is available on `linux`.``. This lets tests complete gracefully instead of failing with a generic driver error.

## Browser fallback

A browser context can fail to start for reasons beyond "not installed," most commonly a **broken driver**. For example, a partially downloaded `geckodriver` can exist on disk yet fail to run. That would otherwise make a Firefox context fail and skip. To stay resilient, Doc Detective validates each browser's driver by *executing* it, not just checking that it's present. When the requested browser can't start, Doc Detective first tries to **repair** it once, reinstalling the browser and its driver. The run can then stay on the browser you asked for. It falls back to another available browser only when the repair doesn't help.

The [`browserFallback`](/reference/schemas/config) config option (or the `--browser-fallback` CLI flag) controls this fallback:

- **`auto`** (default): fall back to any other available browser. When Doc Detective auto-selected the browser, the context runs on the fallback browser and reports `PASS`. When you requested the browser explicitly, the context still runs on the fallback browser but reports `WARNING`. A degraded run therefore never looks like a clean success.
- **`explicit`**: fall back only when Doc Detective auto-selected the browser. Suppose you requested a browser explicitly and its driver fails to run. Doc Detective skips the context with a diagnostic reason instead of substituting another engine.
- **`off`**: never fall back across browsers. Driver validation and the diagnostic skip reason still apply.

Fallback works the same in every direction, so Chrome, Firefox, and Safari/WebKit can each fall back to one another. When no engine can start a session, Doc Detective skips the context with a diagnostic. That diagnostic names the requested browser and the likely cause, such as a partially downloaded driver. The failure stays actionable rather than generic.

You can also set `browserFallback` **per context**, on an individual `runOn` entry. A context-level value takes precedence over the config-level policy for the contexts that entry expands into. You can, for example, default the whole run to `auto` while forcing one Safari-only context to `off`:

```json
{
  "runOn": [
    {
      "platforms": ["windows", "mac", "linux"],
      "browsers": "chrome"
    },
    {
      "platforms": ["mac"],
      "browsers": "safari",
      "browserFallback": "off"
    }
  ]
}
```

You define contexts using an array of context objects. Each context object specifies the target `platforms` (as a string or array) and the target `browsers` (as a string, array, or object).

When Doc Detective runs tests, it evaluates the defined contexts against the current environment. The test runs in a specific browser on a platform when the current platform matches the context and that browser is available. You can specify multiple contexts, and Doc Detective runs the relevant tests in each matching context.

For comprehensive options, see the [context](/reference/schemas/context) reference.

## Specifying contexts

You can specify contexts at three different levels, in order of precedence:

- **Config**: Contexts defined in the main [`config`](/reference/schemas/config) apply to all tests unless overridden.
- **Spec**: Contexts defined in a [`specification`](/reference/schemas/specification) override config-level contexts and apply to all tests within that spec unless overridden.
- **Test**: Contexts defined within a specific [`test`](/reference/schemas/test) override config- and spec-level contexts and apply only to that test.

Contexts are defined using a `runOn` array containing context objects. For example:

```json
{
  ...
  "runOn": [
    {
      "platforms": ["windows", "mac", "linux"],
      "browsers": "chrome"
    },
    {
      "platforms": ["windows", "mac", "linux"],
      "browsers": "firefox"
    },
    {
      "platforms": "mac",
      "browsers": "webkit" // or "safari"
    }
  ],
  ...
}
```

## Browsers

Doc Detective can perform browser-based tests on several browser engines. The following browser names are supported in the `browsers` property:

- **Chrome** (`chrome`): Uses Chromium.
- **Firefox** (`firefox`): Uses Firefox.
- **WebKit** (`webkit`): Uses WebKit. On desktop platforms, the name `safari` can be used as an alias for `webkit`. On an `ios` platform entry, `safari` instead means the real Safari browser on the managed simulator. See [Mobile browsers](#mobile-browsers-android-and-ios).

<Note>
When you use the object format for any browser, you must set `name`. If you omit it (for example, `{ "headless": true }`), Doc Detective can't resolve the browser and skips the context.
</Note>

If a desktop browser sets neither `window` nor `viewport`, Doc Detective gives it a 1200×800 viewport. Screenshots are then the same size on every machine that can fit that viewport, rather than whatever size the browser and operating system choose. Browser sessions that a [`startSurface`](/docs/actions/startsurface) step opens without their own `size` or `viewport` use the context's size.

### Page emulation

A browser object can also set what the page sees about the user's device. Every key is optional. Without a key, the browser uses the host's setting.

| Key | Type | Effect |
|---|---|---|
| `colorScheme` | `"light"` or `"dark"` | The `prefers-color-scheme` value. |
| `locale` | BCP 47 tag, such as `de-DE` | `navigator.language`, `Intl` formatting, and the `Accept-Language` header. |
| `timezone` | IANA name, such as `Europe/Berlin` | The time zone that `Date` and `Intl` use. |
| `deviceScaleFactor` | Number from 0.5 to 4 | `devicePixelRatio`. Screenshots come out at that pixel density. |
| `reducedMotion` | `"reduce"` or `"no-preference"` | The `prefers-reduced-motion` value. |
| `clock` | ISO 8601 date-time, such as `2026-12-03T09:00:00Z` | `Date.now()` and `new Date()` stay at that instant on every page. |

```json
{
  "browsers": {
    "name": "chrome",
    "colorScheme": "dark",
    "locale": "de-DE",
    "timezone": "Europe/Berlin",
    "deviceScaleFactor": 2,
    "reducedMotion": "reduce",
    "clock": "2026-12-03T09:00:00Z"
  }
}
```

Chrome sets every key. Firefox sets every key except `timezone` and `clock`. Safari, Android, and iOS browsers set none of them.

A context that asks for a key its browser can't set reports `SKIPPED`. A fallback browser must also set every key, or it isn't used. The skip reads like this:

```text
Skipped: `firefox` can't set `clock`.
```

Browser sessions that a [`startSurface`](/docs/actions/startsurface) step opens get the same keys. If that session's browser can't set one of them, the step fails rather than skipping.

When Chrome rejects a `timezone` or `clock` value at start, the context fails:

```text
Couldn't set `timezone` to `Europe/Berlin` in `chrome`.
```

These keys are part of the context, so a dark context and a light context of the same browser run separately. To run every variant from one test, use a [`matrix`](#run-once-per-value-with-matrix). To take a screenshot of each variant, see [Capture dark-mode and localized screenshots](/docs/test-docs/capture-screenshots-guide#capture-dark-mode-and-localized-screenshots).

### Chrome (`chrome`)

Available on Windows, macOS, and Linux.

Chrome is the only browser that currently supports video recording via the [`record`](/docs/actions/record) action.

Here's a basic Chrome context for all platforms:

```json
{
  "platforms": ["windows", "mac", "linux"],
  "browsers": "chrome"
}
```

Or using the object format:

```json
{
  "platforms": ["windows", "mac", "linux"],
  "browsers": {
    "name": "chrome"
  }
}
```

#### Chrome Dimensions and Visibility

You can specify browser window dimensions, viewport dimensions, and visibility (`headless`). The [`record`](/docs/actions/record) action records Chrome headed or headless.

```json
{
  "platforms": ["windows", "mac", "linux"],
  "browsers": {
    "name": "chrome",
    "headless": false,
    "window": {
      "width": 1280,
      "height": 800
    },
    "viewport": {
      "width": 1200,
      "height": 720
    }
  }
}
```

<Note>
Doc Detective sizes the `viewport` by resizing the browser window, so the browser/OS **minimum window size** applies. Desktop Chrome, for example, can't render a viewport narrower than about 500px, and this floor applies in headless mode too. When a requested `viewport` is smaller than that floor, the page renders at the larger, realized size. The run still passes, because the constraint is external rather than a test error. Doc Detective logs a `warning` naming the requested and rendered dimensions. The [`startSurface`](/docs/actions/startsurface) action reports the realized size in its `viewport` output as `{ requested, actual }`. Screenshots and measurements then reflect the size the page actually rendered. To capture true sub-500px widths, such as a 375px phone, run the test on an `android` or `ios` platform. The device's own screen then sets the dimensions. A headed Chrome window also can't grow larger than the display. A viewport bigger than the screen renders at the largest size that fits. Headless browsers aren't limited this way.
</Note>

### Firefox (`firefox`)

Available on Windows, macOS, and Linux.

Here's a basic Firefox context:

```json
{
  "platforms": ["windows", "mac", "linux"],
  "browsers": "firefox"
}
```

#### Firefox Dimensions and Visibility

You can specify dimensions and visibility (`headless`). Headless Firefox can't be recorded, so to record Firefox with the [`record`](/docs/actions/record) action, set `headless` to `false`. While [`autoRecord`](/docs/test-docs/automatic-recording) is on, which is the default, Doc Detective runs headless Firefox headed for you when the host can record the screen.

```json
{
  "platforms": ["windows", "mac", "linux"],
  "browsers": {
    "name": "firefox",
    "headless": true,
    "window": {
      "width": 1024,
      "height": 768
    }
  }
}
```

### WebKit (`webkit` or `safari`)

WebKit testing is primarily associated with Safari on macOS. Doc Detective runs tests using the WebKit driver.

You can use either `webkit` or `safari` as the browser name.

Before running tests with WebKit/Safari on macOS, you might need to enable the driver:

1. Run `safaridriver --enable` in your terminal.
2. Ensure **Develop > Allow Remote Automation** is checked in Safari's menu bar. You might need to enable the Develop menu first in Safari's Advanced preferences.

*Note: This setup is often handled automatically in CI environments like GitHub Actions.*

Here's a basic WebKit/Safari context for macOS:

```json
{
  "platforms": "mac",
  "browsers": "webkit" // or "safari"
}
```

#### WebKit/Safari Dimensions

You can specify window or viewport dimensions. WebKit/Safari does **not** support headless mode.

```json
{
  "platforms": "mac",
  "browsers": {
    "name": "webkit", // or "safari"
    "headless": false, // Headless is not supported
    "viewport": {
      "width": 1440,
      "height": 900
    }
  }
}
```

<Note>
Like Chrome, WebKit/Safari sizes the `viewport` by resizing the window, so the same minimum window-width floor applies. See [Chrome Dimensions and Visibility](#chrome-dimensions-and-visibility).
</Note>

### Mobile browsers (Android and iOS)

With a mobile platform entry (`android` or `ios`), `browsers` means the browser **on the managed device**. Doc Detective boots or reuses the emulator or simulator and drives its browser. `goTo`, `find`, `click`, and `screenshot` behave exactly as on desktop. Element semantics are web DOM rather than native accessibility, and no app descriptor is involved.

Each mobile target supports exactly one browser:

| Target | `chrome` | `safari` | `firefox` | `webkit` |
| :-- | :--: | :--: | :--: | :--: |
| `android` | ✓ | Skipped | Skipped | Skipped |
| `ios` | Skipped | ✓ | Skipped | Skipped |

Unsupported combinations skip the context with a reason naming the supported browser. That's the same non-failing outcome as a `platforms` mismatch. If you omit `browsers` on a mobile entry, the platform's browser fills in automatically, so this is a complete mobile-web context:

```json
{
  "platforms": "android"
}
```

And this single entry runs one web test on four targets (the `ios` leg skips, because Chrome isn't available there):

```json
{
  "platforms": ["windows", "mac", "android", "ios"],
  "browsers": "chrome"
}
```

Things that work differently on a device browser:

- **`safari` means Safari.** On an `ios` entry, `safari` is the device's real Safari (not the desktop `webkit` alias). `webkit` on `ios` is an unsupported combination and skips.
- **The device owns its display.** Authored `window` and `viewport` dimensions, along with `headless: false` on the browser config, are rejected with an error. Set [`device.headless`](/reference/schemas/device-descriptor) to control emulator visibility, and pick a different `device.deviceType` if you need another screen size. (`headless: true` matches the schema default, so it's accepted and ignored.)
- **No browser fallback.** The device browser is part of the device image, so there's no alternative engine to fall back to; [`browserFallback`](#browser-fallback) doesn't apply.
- **One browser per device.** The device browser is the context's only browser surface; tests can't open additional browsers on the device.
- **Native app steps live in separate tests.** A single mobile context can drive the device browser *or* native app surfaces ([`startSurface`](/reference/schemas/startsurface)), but not both. A context mixing them skips with a pointer to split the test.
- **`localhost` is the device's own loopback.** An Android emulator reaches the host machine at `10.0.2.2`, so a local test server at `http://localhost:8092` is `http://10.0.2.2:8092` from the emulator. iOS simulators share the host network, so `localhost` works directly.

Host requirements match native mobile app testing, and Doc Detective checks them automatically. `android` needs any capable host with the Android SDK and hardware acceleration, which `doc-detective install android` prepares. `ios` needs a macOS host with Xcode, which `doc-detective install ios` prepares. Incapable hosts skip with actionable guidance. On Android, Chrome ships with `google_apis` system images, the kind `doc-detective install android` installs. Images without Chrome skip with a pointer.

## Run once per value with `matrix`

To run one test once per locale, theme, or page, list the values in a `matrix` on a context, and reference them as `$$matrix.<key>`. Doc Detective runs the test once per combination of the keys it references. Each combination is its own context, with its own browser session, results, and artifact folder.

```json
{
  "testId": "login",
  "runOn": [
    {
      "platforms": "linux",
      "browsers": {
        "name": "chrome",
        "colorScheme": "$$matrix.variant.theme",
        "deviceScaleFactor": "$$matrix.variant.dpr",
        "locale": "$$matrix.locale"
      },
      "matrix": {
        "locale": ["en-US", "de-DE"],
        "variant": [
          { "theme": "light", "dpr": 1 },
          { "theme": "dark", "dpr": 2 }
        ]
      }
    }
  ],
  "steps": [
    { "goTo": "http://localhost:3000/$$matrix.locale/login" },
    { "screenshot": "login-$$matrix.locale-$$matrix.variant.theme.png" }
  ]
}
```

This test runs four times, once for each locale with each variant.

Each `matrix` key is letters, digits, and `_`. Its value is a list of unique items: either all strings, numbers, or booleans, or all objects whose values are strings, numbers, or booleans. An object value keeps related settings together, such as a theme and its pixel density.

### Values from a file

A key can read its list from a file instead, so a page list or sitemap your site already has drives the test:

```json
{
  "matrix": {
    "page": { "file": "pages.json" },
    "url": { "file": "public/sitemap.xml" }
  }
}
```

- A `.json` file holds an array, under the same rules as a list in the spec.
- An `.xml` file is a sitemap. Each `<loc>` entry is one value. Since each value is a full URL, a step can use it directly: `{ "checkLink": "$$matrix.url" }` checks every page in the sitemap, and `{ "goTo": "$$matrix.url" }` opens each one.
- A relative path resolves against the spec or config file that declares the `runOn`, or against the working directory with `relativePathBase: "cwd"`.
- Doc Detective reads each file once, before any test runs. For each test a `matrix` expands, the log says how many contexts it made, such as `login: 12 contexts from matrix.`

A file that doesn't load stops the run, and the CLI exits `2`:

```text
tests[0]: Couldn't read `matrix` file `/docs/pages.json`.
tests[0]: Couldn't load `matrix` key `page`: `/docs/pages.json` isn't a JSON array.
tests[0]: Couldn't load `matrix` key `page`: `/docs/pages.json` has no values.
tests[0]: Couldn't load `matrix` key `page`: `/docs/pages.json` has values `matrix` doesn't accept.
tests[0]: Couldn't load `matrix` key `url`: `/docs/public/sitemap.xml` has no `<loc>` entries.
tests[0]: Couldn't load `matrix` key `page`: `/docs/pages.txt` must be `.json` or `.xml`.
```

### References

- `$$matrix.<key>` is the key's value. `$$matrix.<key>.<field>` is one field of an object value.
- A whole-string reference becomes the value, with its type. In the example, `deviceScaleFactor` gets the number `2`.
- Doc Detective splices a reference inside a longer string in as text. An object value without a field splices in its values joined with `-`, such as `dark-2`.
- A reference ends at the first character that isn't a letter, digit, `_`, or `.`. After a string, number, or boolean value, a `.` starts plain text again, so `$$matrix.locale.png` is the locale followed by `.png`. After an object value, a `.` names a field.
- References work in the context's own fields and in every step, including the steps a `before` or `after` file adds. The `before` and `after` paths themselves, and a test's own `if` and `description`, take no references. The page emulation keys on a browser take a reference in place of a value. So does the URL of a `goTo`, `checkLink`, or `httpRequest` step, which can start with a reference.
- Doc Detective substitutes each combination's values into that context's copy of the steps. Combinations never see each other's values, even when they run at the same time.

### Which tests a `matrix` multiplies

A test runs once per combination of only the keys that its steps or its context reference. A `matrix` in a config or spec `runOn` reaches every test without a `runOn` of its own, and a test that references none of its keys runs once. On a `runOn` that a test sets itself, a key the test doesn't reference is an error.

### Context IDs and files

Each combination's context ID ends in `~<key>=<value>` for each key, such as `linux-chrome~locale=de-DE~variant=dark-2`. An object value's part is its values joined with `-`. Characters that can't be in a file name become `-`. Results, artifact folders, and `junit` report cases use this ID, and each context in the results lists its values under `matrix`.

A `screenshot`, `record`, `saveState`, or `saveCookie` path must reference every key that has more than one value. Otherwise every combination would write the same file. A path Doc Detective picks itself, such as `"screenshot": true`, is already unique per context.

### Errors

A `matrix` mistake stops the run before any test runs, and the CLI exits `2`. With `exitOnFail: false`, Doc Detective skips the spec and warns instead. The messages:

```text
tests[0]: `$$matrix.foo` names no `matrix` key in context `linux-firefox`.
tests[0]: `$$matrix.variant.size` names no field of `matrix` key `variant`.
tests[0]: `matrix` key `theme` isn't used. Reference it as `$$matrix.theme` or remove it.
tests[0]: step 3's `path` `/docs/login.png` is the same for every `matrix` combination. Add `$$matrix.variant` to it.
tests[0]: `matrix` values `a/b` and `a-b` give the same context ID.
```

To take a screenshot of each variant, see [Screenshot every variant from one test](/docs/test-docs/capture-screenshots-guide#screenshot-every-variant-from-one-test).

## Platforms

Doc Detective can run tests targeting the following platforms:

- Windows (`windows`)
- macOS (`mac`)
- Linux (`linux`) (Tested primarily on Ubuntu)
- Android (`android`), a managed emulator. See [Mobile browsers](#mobile-browsers-android-and-ios) for web tests and [startSurface](/reference/schemas/startsurface) for native apps.
- iOS (`ios`), a managed simulator on macOS hosts only. It uses the same references as Android.

When you specify one or more desktop platforms in a context, Doc Detective runs the associated tests only on a matching operating system. If `platforms` is omitted, it defaults to the current platform.

Mobile platforms name the **target** the test runs against, not the host. An `android` context runs on any host capable of running the emulator, and an `ios` context on any macOS host with Xcode. Incapable hosts skip the context with guidance instead of failing.

The desktop platforms (`windows`, `mac`, and `linux`) run browser tests and, on Windows and macOS, [native desktop app tests](/docs/actions/startsurface). The mobile platforms run either browser (web) tests or native app tests on a managed device. One context drives one surface, not both. The context's [`device`](/reference/schemas/device-descriptor) field sets the default device. `android` runs on a managed emulator, and `ios` runs on a managed simulator. For native apps, see [Run on an Android emulator](/docs/actions/startsurface#run-on-an-android-emulator) and [Run on an iOS simulator](/docs/actions/startsurface#run-on-an-ios-simulator). For web tests, see [Mobile browsers](#mobile-browsers-android-and-ios). Because iOS tests run only on a macOS host, an `ios` context on Windows or Linux skips with a reason.

For example, this context targets only macOS:

```json
{
  "platforms": "mac",
  "browsers": "chrome"
}
```

This context targets Windows or Linux:

```json
{
  "platforms": ["windows", "linux"],
  "browsers": "firefox"
}
```

## Requirements (`requires`)

Use `requires` to gate a context on host capabilities beyond the operating system: commands on the PATH, files on disk, or environment variables. If any requirement is unmet, Doc Detective skips the context (the same non-failing outcome as a `platforms` mismatch) and reports each missing requirement.

`requires` accepts three shapes:

- A string names one required command:

  ```json
  {
    "platforms": ["windows", "mac", "linux"],
    "requires": "node"
  }
  ```

- An array names several required commands (all must be present):

  ```json
  {
    "requires": ["node", "ffmpeg"]
  }
  ```

- An object checks commands, files, and environment variables. File paths support `$VAR` expansion, and `$HOME` falls back to `USERPROFILE` on Windows. Environment variables must have a non-empty value.

  ```json
  {
    "platforms": ["mac", "linux"],
    "requires": {
      "commands": ["claude"],
      "files": ["$HOME/.config/app.toml"],
      "env": ["ANTHROPIC_API_KEY"]
    }
  }
  ```

All entries combine with AND. A context can consist of only a `requires` gate: with `platforms` omitted, it runs on the current platform whenever the environment meets every requirement.

You don't need `requires` for browsers or drivers, because Doc Detective's own preflight detects, installs, and repairs those automatically.

### Contexts in a Config (`config.json`)

Specify contexts in the top-level `runOn` array. These apply to all tests unless overridden.

```json
{
  "input": ".",
  "outputDir": "output",
  "runOn": [
    {
      "platforms": ["windows", "mac", "linux"],
      "browsers": "chrome"
    },
    {
      "platforms": ["windows", "mac", "linux"],
      "browsers": "firefox"
    },
    {
      "platforms": "mac",
      "browsers": {
        "name": "webkit",
        "window": { "width": 1280, "height": 800 }
      }
    }
  ]
}
```

### Contexts in a Specification (`*.spec.json`)

Specify contexts in the spec's `runOn` array. These override config-level contexts for tests within this spec.

```json
{
  "description": "Specification for login tests",
  "runOn": [
    {
      "platforms": ["windows", "mac"],
      "browsers": "chrome"
    }
  ],
  "tests": [
    // ... tests in this spec will run on Chrome on Windows & Mac
  ]
}
```

### Contexts in a Test

Specify contexts in the test's `runOn` array. These override config- and spec-level contexts for this specific test.

```json
{
  "description": "Main application specification",
  "tests": [
    {
      "description": "Test login form on Windows/Chrome only",
      "runOn": [
        {
          "platforms": "windows",
          "browsers": "chrome"
        }
      ],
      "steps": [
        // ... steps for this test
      ]
    },
    {
      "description": "Test dashboard on all default contexts",
      // No runOn here, inherits from spec or config
      "steps": [
        // ... steps for this test
      ]
    }
  ]
}
```

## Contexts and multiple browsers

`browsers` does two jobs. It names the test's **default browser surface**, and when it lists several engines it fans the test out to run once per engine. A test can also open **additional** browsers at runtime with a `goTo` step's `surface` field. See [Test across multiple tabs, windows, and browsers](/docs/test-docs/multiple-tabs-and-windows). Only `goTo` opens those browsers, and `runOn` never lists them.

Pin a browser **or** fan out, but not both. The engine fan-out suits browser-*agnostic* tests. A test that pins `surface: { "browser": "firefox" }` in its steps would open Firefox alongside every matrix engine, so give it a single `browsers` entry instead.
