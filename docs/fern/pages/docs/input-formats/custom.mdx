You can define custom input formats and extend existing formats by modifying your [configuration file](/reference/schemas/config). This allows you to support new file types or customize test detection for your specific documentation patterns.

## Creating a custom file type

To define a custom file type, add an entry to the `fileTypes` array in your configuration:

```json
{
  "fileTypes": [
    {
      "name": "custom-format",
      "extensions": ["custom", "cst"],
      "inlineStatements": {
        "testStart": ["## TEST START:(.*)"],
        "testEnd": ["## TEST END"],
        "step": ["## STEP:(.*)"]
      },
      "markup": []
    }
  ]
}
```

### Configuration properties

A file type needs `extensions`, `extends`, or both. A key Doc Detective doesn't recognize makes the config invalid.

- `name`: A descriptive name for the file type.
- `extensions`: The file extensions to process with this file type.
- `extends`: A built-in file type to start from: `markdown`, `asciidoc`, `html`, or `dita`.
- `inlineStatements`: Regular expressions that find [inline test statements](/docs/test-docs/inline). Each statement's first capture group, or else the whole match, is the statement's content.
  - `testStart`: Starts a test.
  - `testEnd`: Ends the current test.
  - `ignoreStart` and `ignoreEnd`: Mark a section to skip.
  - `step`: Adds a step to the current test.
  - `in`: Reads statements from parsed nodes, such as comments, instead of raw text. See [Selectors](selectors).
- `markup`: Definitions that detect steps from your content.

## Adding custom markup patterns

Markup patterns define how Doc Detective extracts tests from your documentation content. Each pattern includes:

- `name`: Descriptive name for the pattern
- `regex`: Array of regular expressions to match content
- `actions`: Array of actions to generate when pattern matches

A `regex` pattern matches the file's raw text, including code samples. To match parsed structure instead, such as links, bold text, or code blocks, use a [selector](selectors).

### Example: Custom Markdown pattern

Add a pattern to detect custom syntax for API calls:

```json
{
  "fileTypes": [
    {
      "name": "markdown",
      "extensions": ["md", "markdown", "mdx"],
      "markup": [
        {
          "name": "apiCall",
          "regex": ["API:\\s*(GET|POST|PUT|DELETE)\\s+`([^`]+)`"],
          "actions": [
            {
              "httpRequest": {
                "method": "$1",
                "url": "$2"
              }
            }
          ]
        }
      ]
    }
  ]
}
```

This pattern matches content like:
```markdown
API: GET `https://api.example.com/users`
```

And generates:
```json
{
  "httpRequest": {
    "method": "GET",
    "url": "https://api.example.com/users"
  }
}
```

### Using capture groups

Regular expression capture groups (numbered $1, $2, etc.) are substituted into the action definition:

```json
{
  "name": "customFind",
  "regex": ["Find the (\\w+) element"],
  "actions": [
    {
      "find": {
        "selector": "aria/$1",
        "timeout": 5000
      }
    }
  ]
}
```

Matches "Find the button element" and generates:
```json
{
  "find": {
    "selector": "aria/button",
    "timeout": 5000
  }
}
```

### Default actions

For basic patterns, you can use action shortcuts. Doc Detective substitutes the first capture group (or entire match) into the default location:

```json
{
  "name": "simpleClick",
  "regex": ["Click: (\\w+)"],
  "actions": ["click"]
}
```

This is equivalent to:
```json
{
  "name": "simpleClick",
  "regex": ["Click: (\\w+)"],
  "actions": [{ "click": "$1" }]
}
```

## Extending existing formats

You can extend existing formats by adding patterns to the default configuration. Doc Detective merges your custom patterns with the built-in patterns.

### Example: Enhanced Markdown

Add patterns for RST-style directives in Markdown:

```json
{
  "fileTypes": [
    {
      "name": "markdown",
      "extensions": ["md", "markdown", "mdx"],
      "markup": [
        {
          "name": "noteDirective",
          "regex": ["\\.\\. note::\\s*([^\\n]+)"],
          "actions": ["find"]
        },
        {
          "name": "codeDirective",
          "regex": ["\\.\\. code::\\s*(\\w+)\\s*\\n\\s+([\\s\\S]+?)\\n\\n"],
          "actions": [
            {
              "runCode": {
                "language": "$1",
                "code": "$2"
              }
            }
          ]
        }
      ]
    }
  ]
}
```

## Running files as shell commands

Not every custom file type contains inline tests or markup patterns. Sometimes the file itself is the test: a script, a notebook, or any file you'd normally run from a shell. For these cases, define an executable file type that maps an extension to a `runShell` command. Doc Detective turns each matching file into a single test with one `runShell` step. Pointing it at the file then runs the file and asserts that it exits cleanly.

An executable file type needs only two properties:

- `extensions`: The file extensions to run with this command.
- `runShell`: The [`runShell`](/docs/actions/runshell) step to perform. Use `$1` as a placeholder for the path of the matched file.

For example, this configuration runs every `.js` file with Node.js, every `.py` file with Python, and runs Jupyter notebooks through `jupyter nbconvert`:

```json
{
  "fileTypes": [
    {
      "name": "JavaScript",
      "extensions": "js",
      "runShell": {
        "command": "node $1"
      }
    },
    {
      "name": "Python",
      "extensions": "py",
      "runShell": {
        "command": "python $1"
      }
    },
    {
      "name": "Jupyter Notebooks",
      "extensions": "ipynb",
      "runShell": {
        "command": "jupyter",
        "args": ["nbconvert", "--to", "script", "--execute", "$1", "--stdout"]
      }
    }
  ]
}
```

The `runShell` value accepts the same fields as a [`runShell`](/docs/actions/runshell) step, so you can assert on exit codes with `exitCodes` and on output with `stdio`. A file whose command exits with a non-zero code fails the test, as does one whose output doesn't match. That mirrors a standalone `runShell` step.

A file type is either a markup file type or a `runShell` file type, not both. When a file type defines `runShell`, Doc Detective runs the file as a command and doesn't parse it for inline tests or markup.

## Example: Custom documentation format

Here's a complete example for a hypothetical custom documentation format:

```json
{
  "fileTypes": [
    {
      "name": "custom-docs",
      "extensions": ["cdoc"],
      "inlineStatements": {
        "testStart": ["TEST\\[(.*?)\\]"],
        "testEnd": ["END_TEST"],
        "step": ["STEP\\[(.*?)\\]"]
      },
      "markup": [
        {
          "name": "navigate",
          "regex": ["@navigate\\s+(.+)"],
          "actions": ["goTo"]
        },
        {
          "name": "click",
          "regex": ["@click\\s+\"([^\"]+)\""],
          "actions": ["click"]
        },
        {
          "name": "type",
          "regex": ["@type\\s+\"([^\"]+)\""],
          "actions": ["type"]
        },
        {
          "name": "verify",
          "regex": ["@verify\\s+(.+?)\\s+contains\\s+\"([^\"]+)\""],
          "actions": [
            {
              "find": {
                "selector": "$1",
                "elementText": "$2"
              }
            }
          ]
        }
      ]
    }
  ]
}
```

This configuration supports a custom format like:

```
TEST[testId: "custom-test"]

# Getting Started

@navigate https://example.com
@click "Login"
@type "username"
@verify #welcome contains "Welcome"

END_TEST
```

## Testing custom patterns

To test your custom patterns:

1. Create a sample documentation file in your format
2. Add test comments or content that matches your patterns
3. Run Doc Detective with the `--input` flag pointing to your file
4. Check the generated test results to verify patterns were detected correctly

<Tabs>
  <Tab title="NPX" language="npx">

```bash
npx doc-detective --input sample.cdoc --config custom-config.json
```

  </Tab>
  <Tab title="Docker" language="docker">

```bash
docker run -v .:/app docdetective/docdetective --input /app/sample.cdoc --config /app/custom-config.json
```

<Note>
The `-v` argument mounts your current directory (`.`) to `/app` in the container.
</Note>

  </Tab>
</Tabs>

## Best practices

- **Start with basics**: Begin with basic patterns and add complexity as needed
- **Test thoroughly**: Validate patterns with various input examples
- **Use descriptive names**: Give patterns descriptive names so you can understand their purpose
- **Document patterns**: Add comments in your config to explain custom patterns
- **Consider escaping**: Properly escape special characters in regex patterns
- **Optimize regex**: Use specific patterns to avoid unintended matches
- **Version control**: Track configuration changes to understand pattern evolution

## Common use cases

Custom input formats are useful for:

- **Proprietary formats**: Internal documentation formats used by your organization
- **Legacy systems**: Older documentation systems with specific markup
- **Domain-specific languages**: DSLs for specialized documentation
- **Enhanced detection**: More sophisticated pattern matching for existing formats
- **Tool integration**: Custom formats from specific authoring tools
