Selectors let a [custom file type](/docs/input-formats/custom) match **document structure** instead of raw text. Doc Detective parses Markdown, MDX, HTML, DITA/XML, and AsciiDoc files into semantic nodes—comments, code blocks, links, images, bold and italic text, prose runs, and elements—and your configuration describes which nodes become tests and steps.

Compared to regular expressions, selectors can't produce a whole class of false positives. A comment inside a code fence is code, not a statement. An image can never match a link selector. Attribute matching doesn't care about quoting style or attribute order.

Selectors are opt-in. The built-in `markdown`, `html`, `dita`, and `asciidoc` file types keep their regular expressions, so upgrading never changes what an existing configuration detects. That includes statements the regular expressions find inside code blocks. The `mdx` built-in is the one selector-based built-in, and you choose it explicitly (see [Structure-aware MDX](#structure-aware-mdx)).

## How files get parsed

When a file type uses selectors, Doc Detective picks a parser per file from its extension—there's nothing to configure:

| Extensions | Parser |
|---|---|
| `md`, `markdown`, `mdown`, `mkd`, `mkdn` | Markdown (CommonMark + GFM) |
| `mdx` | MDX (Markdown + JSX, with `{/* … */}` comments and JSX components as elements) |
| `html`, `htm`, `xhtml` | HTML (standards-conformant) |
| `dita`, `ditamap`, `xml` | XML (entities decoded by the parser) |
| `adoc`, `asciidoc`, `asc` | AsciiDoc (comments, listings, macros, inline formatting) |

Files with other extensions fall back to the parser for the file type's `name` or `extends`. When no parser applies, only regular-expression definitions run for that file. If a file fails to parse (for example, malformed XML), that file degrades to regular-expression detection, and Doc Detective skips its selector definitions.

## Inline statements: where they live

For parsed file types, `inlineStatements.in` lists the **containers** whose text Doc Detective reads as potential statements (`test`, `test end`, `step`, `test ignore start`, `test ignore end`). One shared grammar parses the statement text. By that point, the parser has already stripped the wrapper syntax.

```json
{
  "inlineStatements": {
    "in": ["comment"]
  }
}
```

For Markdown, that single `"comment"` entry covers `<!-- test -->` comments and every `[comment]: #` quote variant: they all normalize to the same comment nodes. In MDX, `{/* test */}` expression comments and `<!-- test -->` comments do too.

A container can also be a filtered node with a `value` field path when the statement text lives somewhere other than the node's content. A DITA file type can use both forms:

```json
{
  "inlineStatements": {
    "in": [
      "comment",
      {
        "element": { "tag": "data", "attributes": { "name": "^doc-detective$" } },
        "value": "attributes.value"
      }
    ]
  }
}
```

And an AsciiDoc file type can use a filter to keep the `// (test …)` parenthesis grammar while ignoring ordinary comments:

```json
{
  "inlineStatements": {
    "in": [
      { "comment": { "matches": "^\\(\\s*([\\s\\S]*?)\\s*\\)$" }, "value": "match.1" }
    ]
  }
}
```

Regular-expression statement properties (`testStart`, `step`, …) still work and can coexist with `in`. For example, a DITA file type can keep matching `<?doc-detective …?>` processing instructions with `testStart` and `step` patterns, since processing instructions aren't containers.

## Markup definitions: the kind is the key

A selector-based markup definition names exactly one node **kind** as its key—the same pattern steps use (`{"goTo": …}`, `{"find": …}`):

```json
{
  "name": "runCode",
  "codeBlock": {
    "language": ["bash", "python", "py", "javascript", "js"],
    "metaExcludes": "testIgnore"
  },
  "captures": ["language", "content"],
  "actions": [
    { "unsafe": true, "runCode": { "language": "$1", "code": "$2" } }
  ]
}
```

`captures` maps node fields, in order, to `$1..$n` for action substitution. An empty kind object (`"strong": {}`) matches every node of that kind, and two kinds have scalar shorthands: `"codeBlock": "bash"` means `{ "language": "bash" }`, and `"element": "uicontrol"` means `{ "tag": "uicontrol" }`.

### Kinds and their options

| Kind | Matches | Options | `captures` fields |
|---|---|---|---|
| `comment` | non-rendered author notes | `matches`, `excludes` | `content`, `match.<n>` |
| `codeBlock` | fenced/source blocks | `language` (string or array, where `""` matches a bare fence), `metaMatches`, `metaExcludes`, `attributes`, `contentMatches`, `contentExcludes` | `language`, `meta`, `content`, `attributes.<name>`, `match.<n>` |
| `link` | hyperlinks | `url`, `text`, `attributes`, `precededBy`, `followedBy` | `text`, `url`, `title`, `attributes.<name>` |
| `image` | images | `src`, `alt`, `attributes`, `precededBy`, `followedBy` | `src`, `alt`, `attributes.<name>` |
| `strong` / `emphasis` | bold / italic text | `text`, `precededBy`, `followedBy` | `text` |
| `text` | prose runs (never inside code or comments) | `matches`, `excludes` | `match.<n>` |
| `element` | named elements (HTML/XML tags, MDX JSX components) | `tag` (string or array), `attributes`, `contentMatches`, `contentExcludes`, `precededBy`, `followedBy` | `tag`, `content`, `attributes.<name>`, `match.<n>`, `then.<field>` |

Option semantics:

- **`attributes`**—a map of attribute name to matcher: a regular-expression string, or `true` to require the attribute exists. The expression matches anywhere in the value, so `"doc-detective"` also matches `doc-detective-notes`. Anchor it (`"^doc-detective$"`) for an exact value. Classes are one space-separated value, so match a single class with `"(?:^|\\s)screenshot(?:\\s|$)"`. Where attributes come from depends on the format:
  - **Markdown**: Kramdown/Pandoc-style attribute lists on images, links, and code fences. `{: .screenshot}`, `{.screenshot}`, and `{: #results .screenshot width="800"}` all normalize the same way (`.cls` → `class`, `#id` → `id`, `key="val"` → named attribute).
  - **MDX**: the same attribute lists, plus JSX component props on `element` nodes (`<Button label="Save" />` exposes `label`).
  - **HTML and XML**: the native element attributes.
  - **AsciiDoc**: the bracket attribute list (`image::x.png[alt, role=screenshot]`).
- **`matches`/`contentMatches`**—a regular expression the node's content must match. Its parenthesized match groups become `match.1`, `match.2`, … `captures` paths. `excludes`/`contentExcludes` reject matches.
- **`precededBy` / `followedBy`**—regular expressions tested against the raw source adjacent to the node, for verb-context patterns like "Click **X**" (`"precededBy": "\\b[Cc]lick\\s+$"`). When the match touches the node, the step's recorded source span extends over it.
- **`followedBy` with `then`**—chains a second node for sequence patterns. The chained node's fields map to `then.<field>` paths. For example, this definition turns DITA's "Type `<userinput>` into the `<uicontrol>`" sentences into steps:

```json
{
  "name": "typeIntoUiControl",
  "element": {
    "tag": "userinput",
    "precededBy": "\\b(?:[Tt]ype|[Ee]nter|[Ii]nput)\\s+$",
    "followedBy": {
      "text": "^\\s+(?:in|into)(?:\\s+the)?\\s+$",
      "then": { "element": { "tag": "uicontrol" } }
    }
  },
  "captures": ["content", "then.content"],
  "actions": [{ "type": { "keys": "$1", "selector": "$2" } }]
}
```

### More examples

Screenshot an image by attribute—you can match and reference any attribute-list attribute, not just classes:

```json
{
  "name": "screenshotToPath",
  "image": { "attributes": { "class": "(?:^|\\s)screenshot(?:\\s|$)", "path": true } },
  "captures": ["src", "attributes.path"],
  "actions": [{ "screenshot": "$2" }]
}
```

Click a JSX component in MDX:

```json
{
  "name": "clickNamedButton",
  "element": { "tag": "Button", "attributes": { "label": true } },
  "captures": ["attributes.label"],
  "actions": ["click"]
}
```

Check links only when they're real hyperlinks (images can't match):

```json
{
  "name": "checkHyperlink",
  "link": { "url": "^https?://" },
  "captures": ["url"],
  "actions": ["checkLink"]
}
```

## Mixing selectors and regular expressions

A markup definition is selector-based when it has a kind key, and regular-expression-based when it has `regex`—one definition can't be both, but one file type freely mixes definitions of each style, and `extends` merges them across built-ins and your overrides. For example, extend `markdown` and add selector definitions: the built-in regular expressions keep running, and your selectors run alongside them.

## Structure-aware MDX

The `mdx` built-in uses selectors throughout. It reads `{/* … */}` expression comments, `<!-- -->` comments, and `[comment]: #` definitions as statements. It exposes JSX components as `element` nodes, and it applies the same link, image, bold, prose, and code-block definitions as the Markdown built-in, in selector form.

The `markdown` built-in still claims `.mdx` files, so `mdx` only takes over when you list it first:

```json
{
  "fileTypes": ["mdx", "markdown", "asciidoc", "html", "dita"]
}
```

Doc Detective uses the first file type whose extensions include the file's extension. With `mdx` listed first, `.mdx` files get structure-aware detection, and every other file keeps the built-in regular expressions.
