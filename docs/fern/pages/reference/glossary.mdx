This glossary defines key terms and concepts used in Doc Detective documentation.

## Action

A command that Doc Detective performs within a [step](#step) of a test. Actions include tasks like navigating to a URL, clicking an element, or taking a screenshot. See [Actions](/docs/get-started/how-testing-works) for the complete list.

## AsciiDoc

A lightweight markup language for technical documentation. Doc Detective supports AsciiDoc files with inline and detected tests. See [AsciiDoc input format](/docs/test-docs/input-formats/asciidoc).

## Context

A combination of platform (operating system) and browser where tests run. You can define contexts at the config, spec, or test level to control where tests execute. See [Contexts](/docs/test-docs/platforms-and-browsers).

## CSS selector

A pattern used to select HTML elements on a page. CSS selectors are the recommended way to target elements in Doc Detective tests. See [CSS selectors](/docs/selectors/css).

## Detected tests

Tests automatically generated by Doc Detective based on your documentation source files. Detected tests use [markup definitions](#markup-definition) to identify testable content. See [Detected tests](/docs/test-docs/detected).

## DITA

Darwin Information Typing Architecture, an XML-based format for technical documentation. Doc Detective can extract tests from DITA task topics using semantic markup. See [DITA input format](/docs/test-docs/input-formats/dita).

## ID

A field ending in `Id`, such as `specId`, `testId`, or `stepId`, identifies something you wrote: a [specification](#specification), [test](#test), or [step](#step). Routing targets these IDs with `goToTest` and `goToStep`, and `--spec` and `--test` filter on them. Doc Detective generates an ID when you omit one. Contrast with a [name](#name), which labels something created while tests run.

## Inline tests

Tests defined directly in documentation source files using specially formatted comments. Inline tests keep test definitions close to the content they validate. See [Inline tests](/docs/test-docs/inline).

## Input format

The file format of your documentation source files. Doc Detective supports Markdown, DITA, AsciiDoc, HTML, and custom formats. See [Input formats](/docs/test-docs/input-formats/overview).

## Markup definition

A rule in a file type's `markup` array that turns matching content into test steps. A selector names a kind of parsed node, such as `link`, `strong`, `codeBlock`, or `comment`, and skips look-alike text in code samples. A `regex` pattern matches the file's raw text, code samples included. A definition can use either or both, and the built-in file types use selectors. You add your own definitions in the `fileTypes` configuration. See [Detect tests with selectors](/docs/test-docs/input-formats/selectors) and [Detected tests](/docs/test-docs/detected).

## Markup pattern

Another name for a [markup definition](#markup-definition). A markup pattern can use a selector, a `regex` pattern, or both.

## Name

A `name` field labels something created while tests run, so a later step can refer to it: a [surface](#surface), a background process, or a recording. For example, `closeSurface` stops a background process by its name, and `stopRecord` stops a recording by its name. Contrast with an [ID](#id), which identifies a specification, test, or step you wrote.

## Selector

A pattern used to identify UI elements for interaction in tests. Doc Detective supports CSS selectors and XPath selectors. See [CSS selectors](/docs/selectors/css) and [XPath selectors](/docs/selectors/xpath). For selectors that match content in your documentation source files, see [Markup definition](#markup-definition).

## Specification

The highest-level component of a test suite, also called a test spec. A specification is a collection of [tests](#test) that should run together and can share configuration. See [Tests overview](/docs/get-started/how-testing-works).

## Step

A single action within a [test](#test). Each step performs one action and acts as an assertion that the action completes as expected. See [Tests overview](/docs/get-started/how-testing-works).

## Surface

An addressable target a step acts on. It's either a browser (a whole session, a window, or a tab) or a background process. Steps select a surface with the `surface` field. Omitting it acts on the active surface, which is the most recently opened or focused one. `goTo` opens browser surfaces, `runShell` and `runCode` start process surfaces, and `closeSurface` closes any of them. See [Test across multiple tabs, windows, and browsers](/docs/test-docs/multiple-tabs-and-windows).

## Test

A sequence of [steps](#step) to perform as part of a test specification. Each test has a name and a set of steps that validate documentation accuracy. See [Tests overview](/docs/get-started/how-testing-works).

## Test specification

See [Specification](#specification).

## XPath selector

An XML path expression used to navigate and select elements in HTML or XML documents. XPath selectors provide more complex element selection than CSS selectors. See [XPath selectors](/docs/selectors/xpath).
